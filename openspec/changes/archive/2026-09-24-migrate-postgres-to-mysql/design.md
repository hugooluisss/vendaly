# Design

## Context

`apps/api/src/Infrastructure/Cycle/CycleOrm.php` hardcodes `PostgresDriverConfig`/`Postgres\DsnConnectionConfig`. All 13 migration files under `apps/api/migrations/` are raw SQL passed to `$this->database()->execute(...)` — Cycle's portable schema DSL is not used here, so every Postgres-specific construct is on us to rewrite by hand. Four repository classes under `apps/api/src/Infrastructure/Cycle/Repository/` also embed raw, Postgres-specific SQL. See proposal.md for the "why" (hosting flexibility) and the confirmed scope decisions (MySQL 8, no data migration, host-native MySQL server already provisioned with `dev_vendaly` database + `vendaly_app` user).

## Goals / Non-Goals

**Goals:**
- Every existing capability behaves identically after the swap — this is a pure infrastructure change (hence `skip_specs: true`).
- All Postgres-only SQL — in migrations and repositories — is replaced with MySQL 8-compatible equivalents that preserve the same enforced constraints (including foreign keys and cascade behavior) and the same observable query results.
- `docker exec vendaly-api-1 php bin/migrate.php` runs clean against the empty `dev_vendaly` database, and the full Codeception `Unit` suite (96 tests) passes against it.

**Non-Goals:**
- No data migration from the existing Postgres data — dev-only environment, schema is recreated from scratch.
- No production/VPS deployment configuration — this only covers local `docker-compose` wiring to the host's MySQL server.
- No change to any repository's public interface, service layer, or controller — only what's beneath `Domain/Repository` interfaces changes.

## Decisions

- **Foreign keys: convert every inline column-level `REFERENCES` clause to an explicit `FOREIGN KEY (col) REFERENCES table(col) ON DELETE ...` clause, in every migration that creates or alters a table.** This is the most consequential finding of this design: MySQL's parser accepts Postgres-style inline `REFERENCES` on a column (both in `CREATE TABLE` and in `ALTER TABLE ... ADD COLUMN`) without error, but it does **not** create an actual foreign key constraint from that syntax — only an explicit `FOREIGN KEY (...) REFERENCES ...(...) ON DELETE ...` clause does. Left unconverted, every `ON DELETE CASCADE`/`ON DELETE SET NULL`/`ON DELETE RESTRICT` relationship in the schema (used throughout: `business_members`, `business_hours`, `categories`, `products`, `order_items`, `product_ingredients`, `product_options`, `order_statuses`, `payment_methods`, `customers`, etc.) would silently stop being enforced — no error at migration time, just orphaned rows or failed application-level assumptions later. This must be audited file-by-file, not just the two migrations flagged for other reasons.
- **`BIGSERIAL` → `BIGINT AUTO_INCREMENT`, `TIMESTAMPTZ`/`TIMESTAMP ... DEFAULT now()` → `TIMESTAMP ... DEFAULT CURRENT_TIMESTAMP`, `ADD/DROP COLUMN IF EXISTS` (kept as-is, MySQL 8 supports both)** — mechanical, done alongside the FK rewrite in the same pass over each file, not a separate step, since nearly every migration needs both.
- **`20260922.000000_12_order_status.php`'s `UPDATE ... FROM (subquery) x WHERE o.id = x.id` → `UPDATE orders o JOIN (subquery) x ON o.id = x.id SET ...`.** MySQL 8 supports the window function (`ROW_NUMBER() OVER (PARTITION BY ...)`) used inside the subquery unchanged — only the outer multi-table update syntax needs rewriting to a join.
- **Same migration's `ALTER TABLE orders ALTER COLUMN order_number SET NOT NULL` / `... status_id SET NOT NULL` → `ALTER TABLE orders MODIFY COLUMN order_number INTEGER NOT NULL` / `MODIFY COLUMN status_id BIGINT NOT NULL`** — MySQL's `MODIFY COLUMN` requires redeclaring the column's full type, matching what the same migration used when adding the column (`INTEGER` for `order_number`, `BIGINT` for `status_id`).
- **`CycleCustomerRepository`'s `INSERT ... ON CONFLICT (business_id, phone) DO UPDATE SET id = customers.id RETURNING id` → `INSERT INTO customers (...) VALUES (?, ?) ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id)` followed by `SELECT LAST_INSERT_ID()`.** The unique key on `(business_id, phone)` already exists (`customers_business_phone_unique`). `LAST_INSERT_ID(id)` inside the `ON DUPLICATE KEY UPDATE` clause is the standard MySQL idiom for making `LAST_INSERT_ID()` return the *existing* row's id on a conflict, not just a newly inserted one — this avoids a separate `SELECT ... WHERE business_id = ? AND phone = ?` lookup.
- **`CycleOrderRepository`'s `UPDATE businesses SET next_order_number = next_order_number + 1 WHERE id = ? RETURNING next_order_number - 1 AS order_number` → `UPDATE businesses SET next_order_number = next_order_number + 1 WHERE id = ?` followed by `SELECT next_order_number - 1 FROM businesses WHERE id = ?`, both inside the same transaction the surrounding code already opens.** InnoDB's default `REPEATABLE READ` isolation takes a row lock on the `UPDATE`, and the subsequent `SELECT` within the same transaction reads its own uncommitted write, so no separate `SELECT ... FOR UPDATE` is needed — the existing transaction boundary already provides the same atomicity Postgres's single-statement `RETURNING` gave for free. This should be verified with a concurrency-oriented test (e.g. two orders created back-to-back for the same business get distinct sequential numbers) rather than assumed.
- **`CycleCatalogScanRepository`'s `to_char(date_trunc('day', created_at), 'YYYY-MM-DD')` (used in `SELECT`, `GROUP BY`, and `ORDER BY`) → `DATE_FORMAT(created_at, '%Y-%m-%d')`**, consistently across all three clauses.
- **`CycleBusinessRepository`'s `ILIKE` on `location`/`name` → plain `LIKE`, contingent on those columns using a case-insensitive collation** (`utf8mb4_unicode_ci`, the collation already chosen for `dev_vendaly` when it was created). Since MySQL's default `_ci` collations make `LIKE` case-insensitive, this reproduces `ILIKE`'s behavior without needing `LOWER(...)` wrapping on both sides — verify with a mixed-case search test rather than assuming.
- **Docker wiring: remove the `postgres` service and `postgres_data` volume from `docker/docker-compose.yml` entirely — no replacement database container.** The `api` service instead gets `extra_hosts: ["host.docker.internal:host-gateway"]` and its `DATABASE_URL`/`DB_USER`/`DB_PASSWORD` environment entries change from hardcoded Postgres values to `${DATABASE_URL}`/`${DB_USER}`/`${DB_PASSWORD}` interpolation (no hardcoded fallback for the password), sourced from `docker/.env` — following the same pattern already used there for `WEB_SERVE_FLAGS`/`LOCAL_UID`/`LOCAL_GID`. `docker/.env` already has these three variables set (done ahead of this change, outside its scope) pointing at the host's `dev_vendaly` database. `apps/api/.env` is not read by the containerized app (no `Dotenv` loader in `apps/api/config`/`public`/`bin`) — it's been left as informational only with a note to that effect; this change should not add logic that starts reading it, to avoid a second, inconsistent source of DB config.

## Risks / Trade-offs

- **Missed inline `REFERENCES` → silent loss of cascade-delete enforcement** → mitigate by grepping for `REFERENCES` across every migration file as a checklist (13+ occurrences found across ~10 files) and converting each one; verify afterward via `SHOW CREATE TABLE <table>` or `information_schema.KEY_COLUMN_USAGE` on a couple of the cascade-heavy tables (`business_members`, `categories`, `products`) to confirm the constraints actually exist, not just that `migrate.php` ran without error.
- **`CycleOrderRepository`'s order-number counter under concurrency** → the same-transaction read-after-write relies on the row lock taken by the preceding `UPDATE`; if this repository method is ever called outside an explicit transaction, the guarantee breaks. Confirm (don't assume) that every call site wraps this in a transaction, same as today.
- **Collation-dependent `ILIKE`→`LIKE` swap** → if `dev_vendaly`'s tables end up created with a different collation than assumed (e.g. a `_bin` or `_cs` variant), `LIKE` search behavior silently diverges from the current case-insensitive `ILIKE`. Explicitly set `CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` on the affected migrations' `CREATE TABLE` statements (or via a `SET NAMES`/database default already matching) rather than relying on server defaults.
- **Test suite behavior parity** — the Codeception `Unit` suite's assertions must not need changes; if a test's *setup* needs adjusting (e.g. a raw SQL string used in a test fixture), that's acceptable, but any change to what a test *asserts* is a signal something's actually behaving differently and should be treated as a bug in the port, not fixed by loosening the test.

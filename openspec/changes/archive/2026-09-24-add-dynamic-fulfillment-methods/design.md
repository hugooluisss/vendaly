# Design

## Context

`Business` (apps/api/src/Domain/Entity/Business.php) has 6 fixed fulfillment columns (3 booleans, 3 fees). `OrderService::validateFulfillment()` (lines 167-186) hardcodes a `['pickup'=>bool,'delivery'=>bool,'dine_in'=>bool]` lookup and returns the *type string* (unused by its only caller — `create()` calls it but discards the return value at line 53; `buildOrder()` independently re-reads `$input['fulfillment_type']` directly at line 110). `buildOrder()` computes the fee via a second hardcoded map (line 116). `WhatsAppOrderLink::generate()` has its own third hardcoded match (lines 50-55) and its own third `$type === 'delivery'` gate (line 56). `payment_methods` already solves the "dynamic, owner-named list with snapshot-on-order" problem end to end — `validatePaymentMethod()` (lines 158-165) returns the resolved `PaymentMethod` entity, which `buildOrder()` receives as a parameter and reads `->id`/`->name` from directly (lines 114-115). See proposal.md for motivation and confirmed scope decisions.

## Goals / Non-Goals

**Goals:**
- Fulfillment methods become a `payment_methods`-shaped table with two extra columns (`fee`, `requires_address`), same CRUD scope (add/rename/delete, no reorder), same seed-on-create pattern, same at-least-one-remains guard.
- `validateFulfillment()` returns the resolved `FulfillmentMethod` entity (not a string), exactly mirroring `validatePaymentMethod()`'s existing signature and call pattern, eliminating all three of today's hardcoded fixed-type lookups in one pass.
- Every business (including ones without earlier fulfillment/payment data, since this is a fresh MySQL database with no production data yet) ends up with a valid seeded fulfillment method after migration.

**Non-Goals:**
- No reorder support (matches `payment_methods`' real, working scope — its frontend reorder button already calls a non-existent backend route today; this change does not fix that pre-existing bug, and deliberately does not reproduce it for the new feature).
- No per-method "disable without deleting" state — like payment methods, a method exists or it's deleted; there is no separate enabled/disabled toggle in the dynamic model.
- No change to how delivery address/coordinates themselves are captured, validated (address-or-coordinates, coordinate range checks), or remembered client-side (`delivery-location.service.ts`) — only what *triggers* that capture changes (a flag instead of a string match).

## Decisions

- **New `FulfillmentMethod` entity + `CycleFulfillmentMethodRepository`, mirroring `PaymentMethod`/`CyclePaymentMethodRepository` field-for-field, plus `fee` (nullable decimal, matching `Business::$pickupFee`'s existing type) and `requiresAddress` (bool, default false).** Reusing the proven pattern exactly (rather than inventing a new shape) minimizes risk and keeps the two capabilities' code recognizably parallel for future maintainers.
- **`OrderService::validateFulfillment(Business $business, array $input): FulfillmentMethod`** (return type changes from `string` to the entity): looks up the method by `$input['fulfillment_method_id']` scoped to `$business->id` (like `validatePaymentMethod`'s loop over `findByBusinessId`), throws `DomainException('Invalid or unavailable fulfillment method.')` if not found — replacing the old "not a key of the enabled map" check. Then, if `$method->requiresAddress`, runs the *exact same* address/coordinate validation block that exists today (lines 175-184), completely unchanged — only the gating condition (`$type !== 'delivery'` → `!$method->requiresAddress`) changes.
- **`create()` passes the resolved `FulfillmentMethod` into `buildOrder()`** as a new parameter (alongside the existing `?PaymentMethod $paymentMethod` one), and `buildOrder()` sets `$order->fulfillmentMethodId = $method->id`, `$order->fulfillmentMethodSnapshot = $method->name`, `$order->fulfillmentFeeSnapshot = $method->fee` directly — replacing both the hardcoded fee-lookup map (line 116) and the direct re-read of `$input['fulfillment_type']` (line 110). This removes the dead-return-value smell where `validateFulfillment()`'s result was previously discarded.
- **`Order` entity**: add `fulfillmentMethodId` (nullable int, FK) and `fulfillmentMethodSnapshot` (nullable string) columns, mirroring `paymentMethodId`/`paymentMethodSnapshot` exactly; remove `fulfillmentType`. `fulfillmentFeeSnapshot` (already exists) is kept as-is — its meaning doesn't change, only where its value comes from.
- **`WhatsAppOrderLink::generate()`**: line 50-55's `match` becomes `$order->fulfillmentMethodSnapshot ?? 'Método de entrega no especificado'` (no match needed — the snapshot is already the human-readable name). Line 56's gate becomes `if ($order->deliveryAddress !== null || $order->deliveryLatitude !== null)` — checking for the *presence* of delivery data rather than a type string, which is equivalent in practice (delivery fields are only ever populated when `requiresAddress` was true at order time) and needs no new column on `Order` to track "was this address-requiring."
- **`CatalogService::publicCatalog()`**: the `fulfillment_methods` array-building block (today: `array_filter([$business->pickupEnabled ? [...] : null, ...])`) is replaced with `array_map(fn($m) => ['id'=>$m->id,'name'=>$m->name,'fee'=>$m->fee,'requires_address'=>$m->requiresAddress], $this->fulfillmentMethods?->findByBusinessId($business->id) ?? [])` — textually identical in shape to the adjacent `payment_methods` block one line below it today.
- **`BusinessService`**: `updateProfile()` loses its two hardcoded fulfillment loops entirely (lines ~115-130) — fulfillment methods are no longer part of the profile PATCH payload, exactly like payment methods aren't. `create()` gains one line seeding `FulfillmentMethod{name: 'Consumo en el local', requiresAddress: false, fee: null, position: 0}`, placed alongside the existing payment-method seed. `setPublished()`'s hardcoded 3-way check becomes `count($this->fulfillmentMethods->findByBusinessId($businessId)) === 0` (mirroring the equivalent payment-methods-count check that must already exist there for the payment-methods publish precondition). New methods `addFulfillmentMethod`/`updateFulfillmentMethod`(name/fee/requiresAddress)/`deleteFulfillmentMethod`(guards `count < 2`)/`listFulfillmentMethods`, each a direct copy of its payment-method counterpart with the two extra fields threaded through `updateFulfillmentMethod`.
- **Migration**: create `fulfillment_methods` (mirroring the `payment_methods` migration's table shape plus `fee DECIMAL(12,2) NULL` and `requires_address BOOLEAN NOT NULL DEFAULT FALSE`), backfill one row per business from its current 3 booleans/fees (`pickup_enabled` → "Recolección en tienda" `requires_address=false`; `delivery_enabled` → "Entrega a domicilio" `requires_address=true`; `dine_in_enabled` → "Consumo en el local" `requires_address=false`; each carrying over its existing fee), then a fallback `INSERT ... SELECT 'Consumo en el local' ... WHERE NOT EXISTS (...)` for any business that ends up with zero rows (mirroring the payment-methods migration's own fallback-seed pattern) — this keeps the migration correct even though the current dev database has no data yet. Add `fulfillment_method_id`/`fulfillment_method_snapshot` to `orders`, backfilling `fulfillment_method_snapshot` from the old `fulfillment_type` via the same 3-way label match `WhatsAppOrderLink` uses today (a one-time `CASE` in the migration, not application code). Drop the 6 `businesses` columns and `orders.fulfillment_type` last, after backfill. Use MySQL syntax throughout (explicit `FOREIGN KEY (...) REFERENCES ...(...) ON DELETE ...`, `BIGINT AUTO_INCREMENT`, `TIMESTAMP DEFAULT CURRENT_TIMESTAMP`) per the project's completed Postgres→MySQL migration — this is the same class of correctness concern that migration's design.md flagged (inline `REFERENCES` without an explicit `FOREIGN KEY` clause does not create a real MySQL constraint).
- **Frontend `fulfillment-methods-modal` component**: rewritten to mirror `payment-methods-modal.component.ts`/`.html` structurally (add-input, list with rename/delete, no reorder), with two additions per list item: a fee `<input type="number">` (reusing the existing `clampFee`-style negative-value clamp already built for this component) and a `requires_address` `<input type="checkbox">`. `business-settings.component.ts`'s single `initialFulfillment: FulfillmentSettings` seed becomes `initialFulfillmentMethods: FulfillmentMethod[]`, sorted by `position` exactly like `paymentMethods`/`orderStatuses` already are in that same constructor line.
- **`order-checkout` component**: `selectedMethod` becomes an id (number) instead of a loosely-typed string/object; a `selectedMethodRequiresAddress` getter looks up `catalog.fulfillment_methods.find(m => m.id === this.selectedMethod)?.requires_address` and replaces the `selectedMethod === 'delivery'` template gate; the hardcoded label ternary is replaced by rendering `method.name` directly; `order-payload.ts` sends `fulfillment_method_id` instead of `fulfillment_type`.

## Risks / Trade-offs

- **Migration backfill correctness for the "delivery requires address" mapping** — since `delivery_enabled` is the only one of the 3 old fixed methods that ever collected an address, hardcoding `requires_address=true` only for that one backfilled row is safe and matches every existing order's actual behavior; a business that never had `delivery_enabled` gets no such row at all, which is also correct (nothing to migrate).
- **`WhatsAppOrderLink`'s new "presence of delivery data implies address was required" check** is an inference, not a stored fact — if a future change ever wanted to distinguish "address was required but customer's method changed after the fact" from "address just happened to be present," this would need an explicit boolean on `Order` (e.g. `fulfillment_method_required_address_snapshot`). Not needed today: delivery fields are only ever populated by the checkout flow when the selected method's `requires_address` was true at submission time, and orders are immutable after creation.
- **Every `PublicCatalogAndOrdersTest.php` fulfillment-related test needs its literal `'fulfillment_type' => 'pickup'` input rewritten to `'fulfillment_method_id' => <id>`, and its catalog-shape assertions rewritten** to the new `{id,name,fee,requires_address}` shape — this is the largest test-rewrite surface in the whole change; budget real implementation time for it, not just the production code.

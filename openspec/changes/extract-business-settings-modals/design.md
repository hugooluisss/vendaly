# Design

## Context

`business-settings.component.ts` currently holds `paymentMethods`/`orderStatuses` arrays plus every CRUD method for them, a `fulfillment` object (`FulfillmentSettings`: `pickup_enabled`/`delivery_enabled`/`dine_in_enabled` + fees) edited via plain `[(ngModel)]` bindings and bundled into `saveProfile()`'s payload, all initialized once in the constructor's `getMine()` subscribe callback and rendered in three `<fieldset>` blocks inside the single profile `<form>`. The existing "Editar horarios" button + `hoursModal` boolean + inline `@if (hoursModal) { <app-modal ...>...</app-modal> }` in `business-settings.component.html` is the pattern to generalize. `ModalComponent` (`apps/web/src/app/shared/modal/modal.component.ts`) is a thin, reusable shell: `@Input() title`, `@Output() close`, projects `<ng-content>`. `BusinessApiService.update(id, fields, logo?, coverImage?)` already types `fields` as `Partial<Pick<Business, ... | 'pickup_enabled' | 'delivery_enabled' | 'dine_in_enabled' | 'pickup_fee' | 'delivery_fee' | 'dine_in_fee'>>` and the backend's `BusinessService::updateProfile` already applies each field independently via `array_key_exists` checks — sending only fulfillment fields in an `update()` call is already a fully supported partial update, no backend change needed. Test coverage today is split oddly across `apps/web/src/app/dashboard/business-settings.component.spec.ts` (one payment-method test, two fulfillment tests, plus unrelated profile/QR tests) and `apps/web/src/app/dashboard/business-settings/business-status-settings.component.spec.ts` (full order-status CRUD suite, despite testing `BusinessSettingsComponent` directly via `Object.create(BusinessSettingsComponent.prototype)`).

## Goals / Non-Goals

**Goals:**
- `business-settings.component` no longer contains fulfillment, payment-method, or order-status state, API calls, or template markup — only the profile form, its own save logic, and four modal triggers (hours, fulfillment methods, payment methods, order statuses).
- Every existing fulfillment/payment-method/order-status test assertion still exists, now exercising the new components, using the same `Object.create(<Component>.prototype)` technique already used for order-status tests (fast, no TestBed needed for pure logic).
- No visible or behavioral change for the business owner, **except** the one explicitly requested change: the fulfillment-methods modal saves independently (its own button, its own `update()` call) rather than only persisting when "Guardar perfil" is clicked.

**Non-Goals:**
- No change to `BusinessApiService`, any backend endpoint, or the `PaymentMethod`/`OrderStatus`/`Business` model shapes.
- No change to the hours modal — it stays as today, serving only as the pattern reference.
- No introduction of a shared "list-with-reorder" abstraction across the payment-methods/order-statuses components — some duplication between them (both have an add-input, a reorder-by-swap list, a delete-with-guard) is acceptable at this size; do not build a generic abstraction speculatively.

## Decisions

- **Each new component owns its state entirely and renders its own `<app-modal>` internally** (self-contained), rather than `business-settings.component` owning the boolean + wrapping the `<app-modal>` inline as it does for hours today. `business-settings.component.html` becomes `@if (paymentMethodsModalOpen) { <app-payment-methods-modal [businessId]="businessId" [initialMethods]="paymentMethods" (close)="paymentMethodsModalOpen = false" /> }` (and the equivalent for order statuses) — the new component's own template wraps its list/form content in `<app-modal [title]="'...'" (close)="close.emit()">`. This keeps the "is this modal open" boolean and trigger button in the parent (matching the hours pattern for consistency) while the modal's *content and behavior* live entirely in the child.
- **`businessId` is a required `@Input()`; the initial list (`payment_methods` / `order_statuses`, already fetched by `business-settings.component`'s existing `getMine()` call) is passed as an `@Input()` seed value** rather than having each new component re-fetch from `BusinessApiService.getMine()` itself. This avoids a redundant network call and matches how `business-settings.component` already has this data in hand. No `@Output()` is needed to sync the list back to the parent, since `business-settings.component` doesn't read `paymentMethods`/`orderStatuses` anywhere outside their own fieldsets (verified) — each new component's list is self-contained after the initial seed.
- **Move, don't rewrite, the existing CRUD method bodies.** Every payment-method/order-status method (`addPaymentMethod`, `renamePaymentMethod`, etc.) moves into its new component class essentially unchanged (same `BusinessApiService` calls, same error handling via `NotificationService`, same local-array update-on-success pattern) — this is a location change, not a logic rewrite, keeping risk low. `enabledCount()`'s body is also moved unchanged; only the fulfillment modal's new `save()` method is genuinely new code (a straightforward `BusinessApiService.update()` call following the same success/error notification pattern used everywhere else in this file).
- **Test migration**: `business-status-settings.component.spec.ts`'s entire suite moves to a new `order-statuses-modal.component.spec.ts`, updating only the imported class name and the `Object.create(...)` target — the assertions and setup stay the same shape. The one payment-method test in `business-settings.component.spec.ts` ("blocks deleting the last payment method client-side") moves to a new `payment-methods-modal.component.spec.ts` the same way. The two fulfillment tests ("counts enabled methods..." and "keeps fees available for the round trip") move to a new `fulfillment-methods-modal.component.spec.ts`, retargeting `Object.create(...)` the same way; a new test should be added there for the independent `save()` call (success and error-notification cases, matching the pattern of `business-settings.component.spec.ts`'s existing "business profile save notifications" tests). `business-settings.component.spec.ts` keeps only its profile-save and QR-code tests, which are unaffected.
- **File locations**: `apps/web/src/app/dashboard/business-settings/fulfillment-methods-modal/`, `payment-methods-modal/`, and `order-statuses-modal/`, each with `.component.ts`/`.component.html`/`.component.css`, following this repo's per-component-folder convention (see CLAUDE.md). Nested under `business-settings/` rather than `shared/` since these are specific to that one screen, not generically reusable.
- **Fulfillment-methods modal saves independently, via its own "Guardar" button, calling `BusinessApiService.update()` with only the six fulfillment fields** (no `logo`/`coverImage` args, no other profile fields) — the user explicitly requested this over the alternative (editing a shared-by-reference object with no save button, synced back to the parent for the main form to persist). On success, the component updates its own local state and shows a success notification via `NotificationService`, same pattern as payment-methods/order-statuses' individual mutations.
- **`business-settings.component`'s `saveProfile()` no longer includes `...this.fulfillment` in its payload**, since fulfillment now has its own persistence path — leaving it in would let a stale in-memory `fulfillment` object (from before the modal's independent save) overwrite the just-saved values on the next profile save. `business-settings.component` no longer needs to hold a live `fulfillment` object at all after the initial seed value is handed to the modal — it can keep just enough of the initial fetch to pass as `[initialFulfillment]`.
- **`enabledCount()` (at least one fulfillment method enabled) moves into the new modal**, since it now only gates that modal's own checkboxes and its own save button — it's no longer relevant to `business-settings.component`'s main submit button, which no longer touches fulfillment fields at all.

## Risks / Trade-offs

- **Seeding from an `@Input()` instead of re-fetching** means if `business-settings.component`'s initial `getMine()` call is slow/stale, a modal opens with whatever was last fetched — acceptable, since this matches today's behavior exactly (the fieldsets read from the same arrays today).
- **Duplicated small patterns between the payment-methods and order-statuses components** (add-input + reorder-by-swap + delete-with-guard) — accepted per the Non-Goals; revisit only if a third similar list appears.
- **Fulfillment now saves independently of the rest of the profile** — a business owner editing both the profile fields and fulfillment methods in the same visit now makes two separate save actions instead of one combined save. This is the intended, explicitly-requested behavior change, not an oversight; call it out clearly during manual verification (task 4.x) so it's a known, confirmed change rather than a surprise.
